# 本地私密金库信任建设手册

调研日期：2026-06-07  
适用对象：纯离线、无服务器、Chrome 插件形态的密码管理器。

## 1. 核心原则

密码管理器的信任不是靠一句“本地加密”建立的，而是靠一组用户可以看见、开发者可以验证、社区可以质疑、你能持续兑现的证据。

你的信任建设要围绕五件事：

1. 说清楚：产品收集什么、不收集什么、能防什么、不能防什么。
2. 做得到：产品行为必须和文案一致，不暗中联网、不暗中采集。
3. 查得到：公开隐私政策、安全说明、权限说明、变更记录。
4. 验得了：代码、构建、依赖、加密逻辑尽可能可审查。
5. 扛得住：遇到漏洞、质疑、商店审核、负面反馈时有标准回应。

纯离线产品最大的信任资产是“没有必要拿用户数据”。所以不要把自己包装成大而全的安全平台，而要把“少做、少要、少传、少承诺”变成品牌气质。

## 2. 信任建设优先级

上线前必须做：

| 项目 | 目的 | 交付物 |
| --- | --- | --- |
| 隐私政策 | 证明不采集、不上传、不出售数据 | `PRIVACY.md` + 商店隐私链接 |
| 安全说明 | 说明加密模型和安全边界 | `SECURITY.md` |
| 威胁模型 | 告诉用户能防什么、不能防什么 | `docs/threat-model.md` |
| 权限说明 | 降低安装时的权限焦虑 | `docs/permissions.md` + 商店说明 |
| 备份风险说明 | 避免明文导出带来信任事故 | 产品内提示 + FAQ |
| 自动锁定 | 减少“解锁后明文长期存在”的风险 | 空闲锁定、失焦锁定或手动锁定 |
| 加密备份 | 避免默认导出明文 JSON | 加密导出/导入 |
| 更新日志 | 让用户知道每次更新改了什么 | `CHANGELOG.md` |

上线后 1-2 个版本内做：

- 开源仓库或至少公开核心加密代码。
- CI 自动跑 typecheck、test、build。
- 依赖审计和 release 校验值。
- 安全问题反馈邮箱或 GitHub Security Advisory。
- 公开路线图，标明“不做什么”。

中期再做：

- 第三方安全审计。
- 可复现构建。
- 小额漏洞奖励计划。
- 多浏览器版本和独立官网。

## 3. 用户最关心的 10 个问题

你要提前回答这些问题，不要等用户在评论区追问。

1. 我的密码会上传到服务器吗？
   - 标准回答：不会。当前版本没有账号系统，也没有服务器同步；加密后的金库保存在浏览器本地存储中。

2. 你们能看到我的密码吗？
   - 标准回答：不能。主密码不上传、不保存；账号数据在本机使用主密码派生密钥加密。开发者没有服务器端恢复入口。

3. 忘记主密码怎么办？
   - 标准回答：无法恢复。为了避免开发者或第三方绕过主密码读取金库，本产品不提供主密码找回。

4. 换电脑怎么办？
   - 当前回答：需要导出备份并在新设备导入。生产版本应默认提供加密备份，而不是明文备份。

5. 为什么需要 `storage` 权限？
   - 标准回答：用于在浏览器本地保存加密后的金库。

6. 为什么需要 `clipboardWrite` 权限？
   - 标准回答：用于点击按钮时把用户名、密码或 2FA 验证码写入剪贴板。建议实际测试是否可以移除该权限；如果保留，必须解释清楚。

7. 纯离线是不是绝对安全？
   - 标准回答：不是。它能减少云端泄露和账号体系风险，但不能防御已被恶意软件控制的设备、键盘记录器、恶意扩展、被他人看到的屏幕或用户自己泄露的备份文件。

8. 你用什么加密？
   - 标准回答：当前使用 PBKDF2-HMAC-SHA256 从主密码派生 AES-GCM 256 位密钥，新建金库默认 PBKDF2 600,000 次迭代。每个金库有 salt，每次写入使用新的 IV。

9. 会不会偷偷更新后加入联网？
   - 标准回答：所有版本更新会在 changelog 中说明权限变化、网络能力变化和数据处理变化。任何新增联网能力都必须在隐私政策和商店页明确说明。

10. 和 Bitwarden / 1Password / Google Password Manager 有什么区别？
   - 标准回答：那些产品更适合需要多端同步、自动填充、共享和企业能力的用户。本产品适合想要无账号、纯本机、轻量金库的人。

## 4. 需要公开的文档

建议至少有 6 个文档。

### 4.1 `PRIVACY.md`

核心内容：

```text
# 隐私政策

本扩展不需要注册账号。
本扩展不上传、出售、共享或分析你的账号、密码、网站、用户名、TOTP 密钥或导入文件。
金库数据保存在浏览器本地存储中，并使用主密码派生密钥加密。

当前版本不包含遥测、广告 SDK、第三方统计 SDK 或远程同步服务。

如果未来加入可选同步或可选匿名统计，将默认关闭或在启用前明确征得同意，并更新本政策。
```

必须避免：

- 写“我们可能会收集必要数据”但不解释。
- 说“不收集任何数据”，同时又接入统计 SDK。
- 商店后台隐私披露、官网隐私政策、实际代码行为不一致。

### 4.2 `SECURITY.md`

核心内容：

```text
# 安全说明

## 加密模型
- 主密码不保存、不上传。
- 使用 PBKDF2-HMAC-SHA256 派生 AES-GCM 256 位密钥。
- 新建金库默认 PBKDF2 600,000 次迭代。
- 加密后的金库存储在 chrome.storage.local。

## 明文存在时间
- 解锁后，账号明文只存在于当前扩展弹窗的运行状态中。
- 点击锁定、关闭弹窗或触发自动锁定后清空明文状态。

## 本产品不能防御
- 已感染恶意软件的系统。
- 键盘记录器或剪贴板监听器。
- 恶意浏览器扩展。
- 他人直接访问已解锁设备。
- 用户主动导出的明文备份。

## 漏洞反馈
请通过 security@example.com 或 GitHub Security Advisory 私下报告安全问题。
```

### 4.3 `docs/threat-model.md`

推荐结构：

- 资产：主密码、账号密码、TOTP 密钥、加密金库、明文导出文件。
- 攻击者：远程网站、恶意扩展、本机恶意软件、拿到电脑的人、拿到备份文件的人。
- 防御范围：本地加密、少权限、无云端数据库、锁定清空 state。
- 不防御范围：系统被攻陷、键盘记录、剪贴板监听、社工钓鱼。
- 设计取舍：无账号恢复、无服务器同步、无默认遥测。

### 4.4 `docs/permissions.md`

示例：

```text
# 权限说明

## storage
用途：保存加密后的本地金库。
不会用于：上传、同步或分析用户数据。

## clipboardWrite
用途：用户点击复制按钮时，将用户名、密码或 2FA 验证码写入剪贴板。
不会用于：读取剪贴板内容。
```

注意：如果后续做自动填充，需要新增 host permissions 或 content scripts，信任门槛会明显升高。那时必须单独写“为什么需要读取网页”和“读取范围是什么”。

### 4.5 `CHANGELOG.md`

每个版本都要写：

- 新增功能。
- 修复问题。
- 安全相关变化。
- 权限变化。
- 数据处理变化。

示例：

```text
## 0.2.0
- 新增加密备份导出/导入。
- 新增空闲 60 秒自动锁定。
- 修复 CSV 导入时引号字段解析问题。
- 权限无变化。
- 无新增网络请求或第三方服务。
```

### 4.6 `docs/security-faq.md`

把第 3 节的 10 个问题扩写成 FAQ。这个文档可以直接链接到 Chrome Web Store、README、官网和社区帖子。

## 5. 产品内信任设计

信任不只在文档里，也要出现在关键操作点。

首次创建金库：

- 明确提示“主密码无法找回”。
- 要求用户确认已理解。
- 显示本地保存和加密说明，但不要塞太多术语。

推荐文案：

```text
请记住主密码。它不会上传，也不会被保存；忘记后无法恢复金库。
```

解锁页：

```text
金库保存在本机。解锁后，账号明文只在当前弹窗中临时存在。
```

导出页：

- 默认提供加密备份。
- 明文导出放到高级选项。
- 明文导出需要二次确认。

推荐文案：

```text
明文备份包含可直接读取的密码和 2FA 密钥。请只在可信设备短暂使用，并在迁移完成后删除。
```

复制密码后：

- 可以提示“已复制，建议尽快粘贴；剪贴板可能被其他软件读取”。
- 中期可加入“30 秒后清空剪贴板”选项，但要说明可能覆盖用户当前剪贴板内容。

自动锁定：

- 默认开启。
- 设置项里提供 30 秒、1 分钟、5 分钟、关闭。
- 不建议默认关闭。

## 6. 技术可信度建设

最小可行做法：

1. 保持权限最少。
2. 不接入统计 SDK、广告 SDK、远程配置。
3. 所有依赖锁定在 `package-lock.json`。
4. CI 每次提交跑 `npm run typecheck`、`npm test`、`npm run build`。
5. 发布包只包含必要文件，不带源码草稿、日志、测试数据。
6. 每次 release 附构建产物哈希。

推荐开源策略：

- 如果你愿意开源，优先开源完整仓库。
- 如果暂时不想完整开源，至少公开核心加密、存储和 TOTP 模块。
- 不要只开源“展示版”，实际商店包另有代码；这会损害信任。

可复现构建的简化版：

```text
1. 用户 clone 指定 tag。
2. 执行 npm ci。
3. 执行 npm run build。
4. 对比 dist zip 的 sha256。
```

依赖策略：

- 不为了小功能随便加依赖。
- 前端 UI 依赖越少越好。
- 每月跑一次 `npm audit`，但不要盲目升级大版本。
- 对加密相关逻辑优先使用 Web Crypto，不引入不必要的自研加密库。

## 7. 商店页信任设计

Chrome Web Store 页面需要把信任点前置。

首屏应出现：

- 无需注册账号。
- 不上传金库数据。
- 本地加密保存。
- 权限说明。
- 忘记主密码无法恢复。

不要把“无法恢复”藏起来。这会让一部分用户离开，但留下来的用户更理解产品，也更少产生差评。

商店页 FAQ：

```text
Q: 这个插件会联网吗？
A: 当前版本不需要服务器账号，也不上传金库数据。浏览器商店安装和更新由 Chrome Web Store 处理。

Q: 为什么没有找回密码？
A: 主密码只在本机用于解密金库，不会上传给开发者。我们没有后门恢复入口。

Q: 适合替代 1Password 或 Bitwarden 吗？
A: 如果你需要多端同步、自动填充、共享和团队管理，它们更适合。这个插件适合本机离线保存和快速复制。
```

## 8. 社区信任打法

首发帖不要像广告，要像一次公开审查邀请。

推荐标题：

- “我做了一个纯离线 Chrome 密码金库，想请大家挑安全问题”
- “不联网、无账号的本地密码管理插件，第一版路线图和安全边界”
- “从 Excel/备忘录迁移到本地加密金库，我做了个小工具”

帖子结构：

1. 为什么做。
2. 当前实现了什么。
3. 明确没实现什么。
4. 加密和存储怎么做。
5. 权限为什么只有这些。
6. 已知风险。
7. 希望大家重点审什么。
8. 路线图。

不要在社区里说：

- “比 1Password 更安全。”
- “绝对不会泄露。”
- “本地就是最安全。”

可以说：

- “它减少了云端账号和服务器存储面，但仍依赖你的本机环境安全。”
- “我希望先把安全边界讲清楚，再决定是否加自动填充。”

## 9. 漏洞和事故响应

你需要在出事前写好流程。

漏洞分级：

| 等级 | 示例 | 响应 |
| --- | --- | --- |
| Critical | 可绕过主密码读取金库；明文被自动上传 | 24 小时内确认，尽快下架或热修 |
| High | 加密备份可被错误解密；自动锁定失效 | 72 小时内修复计划 |
| Medium | 明文残留时间过长；导入解析导致数据错位 | 下个版本修复 |
| Low | 文案误导、权限说明不完整 | 文档或小版本修复 |

公开回应模板：

```text
我们已收到关于 [问题] 的报告。
当前确认影响范围是 [范围]。
该问题是否会导致密码明文泄露：[是/否/仍在确认]。
建议用户立即采取的动作：[动作]。
修复版本：[版本/预计时间]。
后续我们会在 changelog 和安全公告中更新细节。
```

原则：

- 不攻击反馈者。
- 不模糊影响范围。
- 不提前承诺“没有任何风险”。
- 安全问题优先于功能迭代。

## 10. 盈利与信任的关系

前期免费是合理的，但免费不等于没有商业策略。

适合你的信任型盈利顺序：

1. 免费核心版：建立用户和口碑。
2. 捐赠/赞助：让支持者为持续维护买单。
3. Pro 买断：只卖增强能力，不锁核心安全能力。
4. 专业支持：为小团队提供离线部署包、文档、培训和问题响应。

不要把这些能力做成付费墙：

- 本地加密。
- 自动锁定。
- 加密备份。
- 隐私保护。
- 安全修复。

可以收费的能力：

- 高级导入向导。
- 多金库。
- 安全笔记和自定义字段。
- 密码健康报告。
- 本地备份历史。
- 可选 WebDAV/本地目录同步。
- 跨浏览器增强版。

原因很简单：安全基础能力如果收费，会破坏信任；效率增强能力收费，用户更容易接受。

## 11. 30/60/90 天计划

30 天内：

- 完成 `PRIVACY.md`、`SECURITY.md`、`docs/threat-model.md`、`docs/permissions.md`。
- 补自动锁定和加密备份。
- 商店页加入权限说明、主密码无法恢复说明。
- 建立反馈渠道。
- 发第一篇“安全边界说明”。

60 天内：

- 开源或公开核心安全模块。
- 建立 CI 和 release 哈希。
- 发布安全 FAQ。
- 收集 20-50 个真实用户反馈。
- 修复导入、备份、锁定相关问题。

90 天内：

- 决定是否完整开源。
- 评估第三方轻量审查。
- 做 Pro 买断方案草案，但不急着上线。
- 建立版本路线图。
- 如果做自动填充，先写权限变更说明和新的威胁模型。

## 12. 判断是否可信的自检表

发布前逐条检查：

- [ ] 文案没有“绝对安全”“无法破解”“军工级”等夸张表达。
- [ ] 隐私政策、商店披露、代码行为一致。
- [ ] 没有未说明的网络请求。
- [ ] 权限和实际功能一一对应。
- [ ] 主密码不会被保存或上传。
- [ ] 默认备份不是明文。
- [ ] 明文导出有强提醒和二次确认。
- [ ] 解锁后有自动锁定。
- [ ] 忘记主密码无法恢复已明确告知。
- [ ] 每次更新都有 changelog。
- [ ] 安全问题有私下报告渠道。
